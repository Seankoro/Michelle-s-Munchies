### 4. [HIGH] Resend rejections are discarded while callers commit "already sent" state, permanently losing emails
- Area: email-external
- Location: `src/lib/email.ts:145`
- Impact: `send()` returns `void` and swallows both the `{ error }` return and any thrown exception (src/lib/email.ts:145-158), so no caller can tell whether an email actually went out. - Failure scenario: Eight customers are on the back-in-stock waitlist for a sold-out bake. Michelle flips the product available; `notifySubscribers` fires eight `resend.emails.send` calls in roughly one second. Those customers are now permanently marked notified, are excluded from the `is("notified_at", null)` filter forever, and never learn the product came back. The same mechanism silently truncates a newsletter campaign while the admin screen reports it was delivered to the full list.
- Fix: Make `send()` return a boolean (or throw) so the caller knows the outcome, then stamp per recipient only on success: move the `notified_at` update inside the loop and apply it to the single row just mailed, and have `sendNewsletterAction` count only successful sends. **HAND-VERIFIED AND FIXED: "create_order_with_items assigns text to the fulfillment_type enum".** Confirmed real against the live database on 2026-07-29 by reproducing the exact insert shape, which failed with `column "f" is of type fulfillment_type but expression is of type text` in both the VALUES and SELECT forms. Every order insert would have failed. Fixed by migration `0033_fix_order_insert_enum_cast.sql`, applied live, then verified end to end: a full order with two item lines inserts with correct defaults, the daily cap refuses an over-limit order, and add_items_to_order moves item rows and totals together. ### 1. [CRITICAL] create_order_with_items assigns text to the fulfillment_type enum, so every order insert fails
- Area: n/a
- Location: `supabase/migrations/0032_atomic_orders_and_confirmed_subscriptions.sql:80`
- Impact: Total ordering outage. create_order_with_items is the only code path that writes an order (src/lib/orders-db.ts:124 for checkout, :252 for admin manual orders), so no customer can place an order and Michelle cannot log a WhatsApp order either. This is a regression introduced by the atomic-insert rewrite: the old PostgREST .insert() let PostgREST cast the JSON string into the enum, but inside plpgsql the value is already typed text and PostgreSQL only provides an explicit-context cast from string types to enums, never an assignment-context one.
- Failure scenario: I ran the deployed function against the live DB inside a rolled-back DO block with a normal payload (pickup, 2099-01-01, one 1000-cent line). It raised SQLSTATE 42804: `column "fulfillment_type" is of type fulfillment_type but expression is of type text`. In the app that surfaces as `Could not create order: ...` from orders-db.ts:164, which placeOrder's generic catch turns into "Something went wrong placing your order." The retry loop does not help: error.code is 42804, not 23505. Note status and payment_status are fine because they are left to their column defaults; fulfillment_type is the only enum the function writes.
- Fix: Cast explicitly: `(p_order->>'fulfillment_type')::public.fulfillment_type`. I patched a copy of the deployed function that way and re-ran the same probe (delivery + address + daily/window caps + one item) inside a rolled-back block; it completed cleanly, so this is the only type error in the function.
### 2. [HIGH] Bundle save deletes all bundle_items before re-inserting, so a failed insert leaves an active, purchasable bundle with no contents
- Area: n/a
- Location: `src/lib/admin-merch.ts:65`
- Impact: `replaceBundleItems` issues an unchecked `delete().eq("bundle_id", ...)` and only then inserts the replacements, with no transaction. If the insert errors, the items are gone permanently while the bundle row keeps `is_active = true` and its price. `rowToBundle` (src/lib/bundles.ts:40) computes `soldOut: items.some(...)` which is `false` for an empty list, and `validateBundleForCheckout` (src/lib/bundles.ts:89) computes `available: (row.bundle_items ?? []).every(...)` which is `true` for an empty list. So checkout accepts the line at full price for zero goods, and the bundle detail page renders "What's inside" as an empty list. The same delete-then-insert pattern is in `replaceBoxItems` (line 171) and `replaceProductOptions` (src/lib/admin-db.ts:639).
- Failure scenario: Michelle edits the "Weekend Set" bundle (S$45, 3 items) and, adjusting a quantity, types a space into the quantity box. src/app/admin/(panel)/bundles/page.tsx:271 evaluates `Math.max(1, parseInt(" " || "1", 10))` → `Math.max(1, NaN)` → NaN. She clicks Save bundle. `updateBundle` succeeds on the bundles row, `replaceBundleItems` deletes all three items, then the insert sends `quantity: null` (JSON.stringify(NaN)) and fails the NOT NULL check. The modal shows "Failed to save bundle items" and does not refresh, so the list still shows "3 items". The storefront now sells Weekend Set at S$45 containing nothing, and the packing slip and bake list for that order are empty.
- Fix: Do the swap in one transaction: add a `replace_bundle_items(p_bundle_id uuid, p_items jsonb)` Postgres function (same pattern as `create_order_with_items` in 0032) and call it, so a failed insert rolls the delete back. Independently, harden `validateBundleInput` in src/lib/admin-actions.ts:372 to reject items whose `quantity` is not a positive integer, fix the NaN-producing handler at bundles/page.tsx:271, and make `rowToBundle`/`validateBundleForCheckout` treat an item-less bundle as sold out rather than available.
### 3. [HIGH] Order placement blocks on an un-timed-out Resend call after the DB commit, so a slow email provider turns a placed order into a duplicate
- Area: n/a
- Location: `src/lib/orders-db.ts:168`
- Impact: createOrder awaits sendOrderEmails after create_order_with_items has already committed. send() in src/lib/email.ts:138-159 wraps the Resend call in try/catch but passes no AbortSignal, and the Resend SDK has no default timeout, so a hung request never rejects and never resolves. ### 4. [HIGH] Admin sign-in has no rate limit, leaving the single admin password open to unlimited guessing
- Area: n/a
- Location: `src/lib/admin-actions.ts:63`
- Impact: adminSignIn is a public Server Action (the /admin/login page is explicitly exempted from the middleware gate, so its action ID ships to any visitor) and it is the only auth entry point in the codebase with no rateLimit() call. Every sibling auth action got one when LOW-15 was fixed — signInWithPassword 10/5min, signUpWithPassword 5/15min, sendMagicLink and sendPasswordReset 5/15min — but the fix only touched src/app/account/actions.ts and missed this fifth entry point. This is a gap in that prior fix, not a re-report of it. The live database has exactly one user, admin@michelles-munchies.com (a guessable address), and that one password is the sole gate on order data, customer PII, refunds, promo codes, and store settings. The comment in rate-limit.ts ("Supabase already throttles its own auth endpoints") does not hold here: the call to GoTrue originates from the Vercel function, so Supabase's per-IP sign-in throttle sees one shared egress IP for the whole site. That bucket either lets the attacker keep guessing or, once tripped, blocks every legitimate customer sign-in too. adminSignIn also returns error.message raw (line 66), which distinguishes "Invalid login credentials" from "Email not confirmed", and returns a distinct "This account doesn't have admin access" (line 69) that confirms when guessed credentials are valid for a non-admin account.
- Failure scenario: An attacker opens /admin/login, reads the Server Action id from the page bundle, and POSTs adminSignIn("admin@michelles-munchies.com", candidate) in a loop from a single IP. Nothing in the app counts, delays, or locks the attempts; after N guesses the correct password returns {ok:true} and the attacker holds a full admin session. Separately, firing that loop hard trips Supabase's shared per-IP sign-in limit, so every real customer attempting to sign in during the attack gets an auth error.
- Fix: Add a rateLimit guard at the top of adminSignIn mirroring the customer path, e.g. `if (!(await rateLimit("admin-sign-in", { limit: 5, windowMs: 15 * 60_000 }))) return { ok: false, error: "Too many attempts. Please wait a few minutes." };` plus a tighter per-email bucket, and collapse both failure branches to one generic constant string ("That email or password is not right.") so the response cannot distinguish wrong-password from valid-but-not-admin.
### 5. [HIGH] Customers can reset their own birthday_rewarded_year via the REST API and re-farm birthday points
- Area: n/a
- Location: `src/lib/birthday.ts:45`
- Impact: grantBirthdayRewards uses profiles.birthday_rewarded_year as its only idempotency guard, but that column is customer-writable. The live profiles RLS policy "Users update own profile" is cmd=ALL-columns UPDATE with qual `auth.uid() = id`, and the authenticated role holds a table-wide UPDATE grant covering birthday, birthday_rewarded_year, referral_code, referred_by, and winback_sent_at. src/app/account/actions.ts:281 writes only four safe fields, but nothing confines a client to that action: the anon key is NEXT_PUBLIC_ and the app itself already writes tables directly from the browser (SavedAddresses.tsx uses supabase.from("addresses").insert), so a direct PostgREST PATCH is inside the app's own model. Points convert to money at point_value_cents (currently 5c each) off any order, so this is a self-service money leak with no admin visibility. Precondition, stated honestly: settings.birthday_reward_points is 0 on the live DB right now, so line 15 short-circuits and the exploit yields nothing today. The moment Michelle sets a non-zero birthday reward in the admin settings screen (the feature flag is already on), it becomes free money every hour.
- Failure scenario: A signed-in customer sends `PATCH /rest/v1/profiles?id=eq.<their own uid>` to the Supabase REST endpoint with the public anon key and their own access token, body `{"birthday":"1990-07-29","birthday_rewarded_year":null}`. RLS permits it (auth.uid() = id). The next hourly cron run matches their birthday, claims the year, and inserts a birthday points_ledger row. They repeat the same PATCH and collect the reward again on the next run, indefinitely, redeeming the balance as order discounts.
- Fix: Revoke customer write access to the server-owned columns instead of relying on the app's narrow update path: `revoke update on public.profiles from anon, authenticated;` then `grant update (full_name, phone, birthday, dietary_prefs) on public.profiles to authenticated;` in a new migration (same shape as 0030's column-scoped re-grant). Optionally also stop the reward from being re-triggerable by a birthday edit by recording grants in points_ledger and checking `reason = 'birthday'` for the current year rather than trusting the profile column.

### 7. [MEDIUM] Every OneMap failure is swallowed and silently downgrades the delivery fee that is charged
- Area: n/a
- Location: `src/lib/onemap.ts:28`
- Impact: `getToken`, `geocodePostal` and `driveDistanceMeters` each end in a bare `catch { return null; }` (src/lib/onemap.ts:28-30, 50-52, 68-70) and return null on any non-OK response, with no console line and no Sentry report. `resolveDeliveryDistanceKm` then falls through to a postal-sector centroid times a road factor (src/lib/delivery-distance.ts:90-94) and returns it as if it were a real driving distance, and `estimateDeliveryFeeAction` catches and falls back again (src/app/checkout/actions.ts:113-120). Nothing appears in the logs or Sentry, so the undercharging continues indefinitely.

Add a short negative cache on `getToken` (e.g. suppress retries for 60s after a failure) so a bad credential does not generate a login POST per request. Consider having `resolveDeliveryDistanceKm` return a flag distinguishing a measured distance from a centroid estimate, so `computeZonedDeliveryFeeCents` can fall back to the flat fee rather than quietly assigning a tier from a guess.

### 12. [MEDIUM] Middleware redirects discard the refreshed Supabase session cookies, silently signing users out
- Area: n/a
- Location: `src/middleware.ts:109`
- Impact: The Supabase cookie plumbing writes refreshed tokens onto the `response` object built at line 45 and reassigned inside setAll (lines 55-61). All three early returns — line 84 (/account guard), line 109 (signed-in visitor on sign-in/sign-up), line 125 (non-admin on /admin) — return a brand-new `NextResponse.redirect(...)` that carries none of those Set-Cookie headers. Mutating request.cookies only propagates through `NextResponse.next({ request })`, never through a redirect. The same three returns also skip the `response.headers.set("Content-Security-Policy", csp)` at line 129, so redirect responses ship without the new CSP.

Past Supabase's ~10s refresh-token reuse window the browser's old token is rejected as "Invalid Refresh Token: Already Used", the session is cleared, and the customer is bounced back to sign-in having lost their session mid-flow. Same path for a signed-in non-admin who opens /admin.
- Fix: Copy the accumulated cookies onto every redirect before returning, e.g. build the redirect as `const redirect = NextResponse.redirect(redirectUrl); response.cookies.getAll().forEach((c) => redirect.cookies.set(c)); redirect.headers.set("Content-Security-Policy", csp); return redirect;` — or factor that into a small `finish(res)` helper used by all four return points.
### 13. [MEDIUM] Per-email rate-limit buckets are silently scoped by IP too, so the email-bombing cap does not bound a distributed attacker
- Area: n/a
- Location: `src/lib/rate-limit.ts:84`
- Impact: rateLimit() unconditionally appends the client IP to the key: `const key = \`rl:${action}:${await clientIp()}\``. Callers that pass an identity in the action string — `auth-magic-link:${normalizedEmail}` (actions.ts:152), `auth-password-reset:${normalizedEmail}` (actions.ts:184), `newsletter-subscribe:${normalized}`, `back-in-stock:${resolved}`, `checkout-intent:${email}` — therefore get a per-(email, IP) counter, not the per-email counter their comments claim ("Per-address throttle so repeat subscribes can't bombard one inbox"). LOW-15's stated fix was a per-IP cap "and, for the two email-sending actions, additionally by normalized email", precisely so a distributed sender could not exhaust the Supabase auth SMTP quota. The identity half of that fix is inert: it is fully defeated by the same IP rotation the per-IP half already assumes. This is an incomplete fix of LOW-15, not a re-report.
- Failure scenario: An attacker with 200 rotating IPs (a cheap proxy pool) POSTs sendPasswordReset("victim@example.com") three times per IP. Each IP passes both gates (the 5/15min global bucket and the 3/hour email bucket are both fresh per IP), delivering 600 password-reset emails to one inbox in minutes. Because every one of those goes through Supabase's auth SMTP, the store's hourly send quota is drained and legitimate customers stop receiving sign-up confirmations and reset links entirely — the exact outcome LOW-15 was filed to prevent.
- Fix: Give rateLimit an explicit subject so identity-keyed buckets are not IP-scoped, e.g. `rateLimit(action, opts, subject?)` where the key is `rl:${action}:${subject ?? await clientIp()}`, and have the four identity call sites pass the normalized email as the subject while keeping their existing IP-keyed global bucket as the first gate.
### 14. [MEDIUM] The password-recovery cookie is never actually cleared, so updatePassword is replayable rather than one-time
- Area: n/a
- Location: `src/app/account/actions.ts:238`

Separately, have /auth/callback distinguish a real recovery exchange from a magic link by checking the exchanged session (e.g. only set the cookie when the exchange came from a recovery-type link) rather than inferring it from the attacker-influenceable `next` path.
